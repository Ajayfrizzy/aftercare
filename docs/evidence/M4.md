## Account lifecycle and workflow review

Deletion requires the session owner, same-origin POST, matching account email, current password, and literal DELETE. Password attempts share the existing throttle. The transaction rechecks the session after password verification, queues owner receipt IDs and removes purchases and the user. Foreign keys remove sessions, artifacts, evidence, agent jobs, cases, drafts, approvals, exports, preferences, and the owner's audit trail. A failed transaction rolls back both deletion and cleanup scheduling. HTTP 202 means active database removal committed. The API worker unlinks queued UUID-named receipt files from the recorded storage root in batches of 32 while awake, retaining failures for retry after one minute. Missing files are treated as already removed. Restoring access to the same storage root is required after a path change. Backup archives, downloaded files, in-flight responses, filesystem remnants and SQLite/WAL forensic erasure are outside this active-store guarantee.

Settings identify export contents as JSON records and references; the payload marks attachmentsIncluded false. The privacy screen handles signed-out, unavailable, retry and success states. Case and approval screens recover current, unexpired, unconsumed approval IDs from the authenticated API after navigation. The recovery actions retain version/hash checks and one-time consumption.
